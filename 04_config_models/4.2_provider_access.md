## 4.2 Kết nối nhà cung cấp mô hình (Provider) & Phương thức xác thực

Ở [Chương 2](../02_setup/2.3_onboarding.md), wizard `openclaw onboard` đã giúp bạn hoàn tất việc gắn khóa API của các nhà cung cấp tích hợp sẵn, mô hình đã có thể gọi được ngay. Mục tiêu của mục này không lặp lại thao tác "kết nối", mà làm rõ 3 vấn đề trọng yếu: Khi nào thì bạn cần viết rõ khối `models.providers`, khi nào thì không cần; làm thế nào để nạp và xoay tua khóa API một cách an toàn; và cách sử dụng các câu lệnh tiêu chuẩn để nghiệm thu trạng thái kết nối.

### 4.2.1 Ba ngả đường: Bạn có thực sự cần viết models.providers?

Các nhà cung cấp tích hợp sẵn trong OpenClaw (như OpenAI, Anthropic, Moonshot...) đều đã công bố sẵn danh mục mô hình mặc định (Default catalog). Đa số các provider tích hợp sau khi hoàn tất xác thực qua `openclaw onboard`, khóa API sẽ được ghi vào tệp `~/.openclaw/agents/<agentId>/agent/auth-profiles.json`, thông thường bạn không cần phải tự tay viết khối `models.providers`; tuy nhiên cũng lưu ý rằng một số quy trình provider / onboarding vẫn có thể đồng bộ cấu hình provider vào `openclaw.json`.

Nói một cách chính xác hơn, bạn chỉ cần viết rõ khối `models.providers` trong các trường hợp sau:

- **Ghi đè hành vi mặc định của provider tích hợp sẵn**: Khi bạn cần tùy biến `baseURL`, thêm Custom HTTP Headers hoặc tùy biến danh sách mô hình.
- **Kết nối các nhà cung cấp tự lưu trữ (Self-hosted) hoặc tùy biến**: Như máy chủ proxy tự dựng hoặc endpoint nội bộ; các nền tảng như OpenRouter hay Ollama đã có sẵn tài liệu/plugin tích hợp, thông thường chỉ khi tùy biến endpoint hoặc danh mục model bạn mới cần viết `models.providers`.

Một sai lầm phổ biến là cố nhồi nhét việc xoay tua nhiều khóa API vào trong `models.providers`. Việc triển khai theo tỷ lệ (Canary), thứ tự ưu tiên profile hoặc danh sách nhiều key dự phòng nên được quản lý qua cơ chế Auth Profiles và `auth.order`; chỉ những biến môi trường khóa tĩnh được provider hỗ trợ rõ ràng mới thích hợp dựa vào cơ chế nạp biến môi trường trực tiếp (Xem chi tiết tại Mục 4.2.5).

Nói cách khác, đối với đại đa số người dùng, sau khi onboard xong bạn chỉ cần chỉ định định danh mô hình trong `agents.defaults.model`:

```javascript
{
  // Provider tích hợp đã được xác thực qua onboarding, không cần viết models.providers
  agents: {
    defaults: {
      model: {
        primary: "openai/gpt-5.5",
      },
    },
  },
}
```

Định danh mô hình luôn tuân theo định dạng chuẩn `provider/model`, trong đó tiền tố `provider` trước dấu gạch chéo bắt nguồn từ danh mục mô hình tích hợp/plugin hoặc từ provider tùy biến khai báo trong `models.providers`; Auth profiles và biến môi trường chỉ cung cấp tài liệu xác thực chứ không có chức năng đăng ký provider mới. Cần đặc biệt lưu ý: **Đường dẫn provider và môi trường runtime không phải là khái niệm cùng một tầng**. Các mô hình agent của OpenAI đều dùng tiền tố chuẩn `openai/*`; việc xác thực thuê bao ChatGPT/Codex OAuth được thể hiện qua Codex/OpenAI auth profile và runtime, các cấu hình cũ dùng tiền tố `openai-codex/*` nên được chuyển đổi sang `openai/*` bằng lệnh `openclaw doctor --fix`. Một số định danh phổ biến (lưu ý các tên dưới đây là ví dụ minh họa định dạng, danh sách model khả dụng thực tế căn cứ theo `openclaw models list`, `openclaw models status --probe` và danh mục chính thức của từng nhà cung cấp):

- `openai/gpt-5.4`, `openai/gpt-5.4-pro`
- `openai/gpt-5.5` (có thể kết hợp với Codex OAuth hoặc OpenAI API Key)
- `anthropic/claude-sonnet-4-6`, `anthropic/claude-opus-4-6`
- `anthropic-vertex/claude-sonnet-4-6` (gọi Claude qua Google Cloud Agent Platform)
- `moonshot/kimi-k2.6` (`moonshotai` là bí danh tương thích lịch sử)
- `zai/glm-5`
- `chutes/<tên_model>` (Nền tảng Chutes, hỗ trợ cả xác thực OAuth và API Key)
- `xai/grok-4.3`; nếu dùng Grok 4.20 beta, cần ghi đầy đủ ID beta, ví dụ: `xai/grok-4.20-beta-latest-reasoning`

### 4.2.2 Các tình huống cần cấu hình tường minh & Ví dụ

Các ví dụ dưới đây dành cho những trường hợp **thực sự cần** khai báo `models.providers`: Provider tùy biến, endpoint tương thích OpenAI nằm sau Proxy, hoặc các hệ thống cần tự quản lý danh mục mô hình. Nếu bạn dùng provider tích hợp và đã hoàn tất xác thực qua onboarding, có thể nhảy thẳng sang Mục 4.2.4 để tìm hiểu các hình thức nạp khóa nâng cao.

**1. Provider Proxy tùy biến**

Khi cần định tuyến yêu cầu gọi mô hình qua máy chủ Proxy nội bộ hoặc endpoint tương thích OpenAI, khối `models.providers.<id>` tối thiểu phải cung cấp `baseUrl` và danh sách `models`, đồng thời chọn đúng bộ điều hợp `api` tương ứng với backend:

```javascript
{
  models: {
    providers: {
      "custom-proxy": {
        baseUrl: "https://my-proxy.internal/v1",
        apiKey: "${CUSTOM_PROXY_API_KEY}",
        api: "openai-completions",
        models: [
          {
            id: "team-fast",
            name: "Team Fast Model",
            input: ["text"],
            contextWindow: 128000,
            contextTokens: 96000,
            maxTokens: 32000,
          },
        ],
      },
    },
  },

  agents: {
    defaults: {
      model: {
        primary: "custom-proxy/team-fast",
      },
    },
  },
}
```

> [!NOTE]
> Nếu bạn chỉ muốn thay đổi khóa API của nhà cung cấp tích hợp sẵn, đừng bao giờ dùng một khối `models.providers` chỉ chứa mỗi trường `apiKey` để ghi đè. Hãy ưu tiên dùng onboarding hoặc lệnh `openclaw models auth` để ghi vào auth profiles, hoặc sử dụng các biến môi trường được provider đó hỗ trợ.

**2. Anthropic Vertex (Gọi Claude qua Google Cloud Agent Platform; nền tảng trước đây tên là Vertex AI, định danh provider vẫn giữ là `anthropic-vertex`)**

Phương thức xác thực: GCP Service Account hoặc Application Default Credentials.
Định danh mô hình nên căn cứ theo đầu ra của `openclaw models list`, `openclaw models status --probe` và tài liệu chính thức của Anthropic / Google Cloud, không nên gắn cứng lâu dài các snapshot cụ thể.

```javascript
{
  // Xác thực qua GCP Application Default Credentials, Service Account hoặc Auth profile sinh từ onboarding;
  // Không nên viết region/projectId thành khối ghi đè models.providers chỉ chứa metadata.
  agents: {
    defaults: {
      model: {
        primary: "anthropic-vertex/<định_danh_claude_khả_dụng>",
      },
    },
  },
}
```

> [!TIP]
> Anthropic Vertex đặc biệt thích hợp cho các đội ngũ đã có sẵn hạ tầng trên Google Cloud Platform: Lưu lượng mạng đi qua đường truyền nội bộ của Google, tận dụng được hệ thống phân quyền IAM và chính sách mạng VPC của GCP, đồng thời chi phí được gom chung vào hóa đơn GCP.

**3. Tự lưu trữ qua Ollama (Self-hosted Ollama)**

`baseUrl`: `http://localhost:11434`
Các định danh mô hình thông dụng: `ollama/gpt-oss:20b`, `ollama/qwen2.5-coder:32b`... (tùy thuộc vào các model bạn đã tải về máy, chi tiết lựa chọn model và yêu cầu VRAM xem tại [Mục 16.3.2](../16_claude_ecosystem/16.3_other_ecosystems.md)).

> [!WARNING]
> Tuyệt đối không dùng đường dẫn tương thích OpenAI như `http://localhost:11434/v1` — tài liệu chính thức đã chỉ rõ việc này sẽ làm hỏng cơ chế gọi công cụ (Tool call), khiến mô hình xuất JSON của tool dưới dạng văn bản thông thường. Bạn bắt buộc phải dùng trực tiếp địa chỉ API gốc của Ollama.

```javascript
{
  models: {
    providers: {
      ollama: {
        baseUrl: "http://localhost:11434",
        apiKey: "ollama-local",
        api: "ollama",
        models: [
          {
            id: "gpt-oss:20b",
            name: "GPT-OSS 20B",
            input: ["text"],
            cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
            contextWindow: 128000,
            maxTokens: 8192,
          },
        ],
      },
    },
  },

  agents: {
    defaults: {
      model: {
        primary: "ollama/gpt-oss:20b",
      },
    },
  },
}
```

> Giá trị `contextWindow` ở đây chỉ là gợi ý dung lượng cho phía OpenClaw, không đồng nghĩa là phía server Ollama chắc chắn sẽ cấp phát cùng dung lượng context đó khi chạy; giá trị thực tế phụ thuộc vào VRAM, biến `OLLAMA_CONTEXT_LENGTH`, tệp Modelfile và tham số `params.num_ctx`, xem chi tiết tại [Mục 16.3.2](../16_claude_ecosystem/16.3_other_ecosystems.md).

### 4.2.3 OpenRouter

`baseUrl`: `https://openrouter.ai/api/v1`
Bộ điều hợp API: `openai-completions`
Biến môi trường: `OPENROUTER_API_KEY`
Ví dụ định danh mô hình: `openrouter/<provider>/<model>`. Tên mô hình cụ thể căn cứ theo danh mục hiện tại của OpenRouter và đầu ra của `models list` / `models status --probe`.

Cấu hình biến môi trường:

```bash
export OPENROUTER_API_KEY="sk-or-xxx..."
```

Cấu hình mẫu (OpenRouter đã có plugin provider và luồng onboarding riêng, thông thường bạn chỉ cần xác thực và chọn model; đừng viết khối ghi đè `models.providers.openrouter` chỉ chứa `apiKey`/`baseUrl` mà thiếu mảng `models`):

```javascript
{
  agents: {
    defaults: {
      model: {
        primary: "openrouter/<provider>/<model>",
      },
    },
  },
}
```

### 4.2.4 Cơ chế nạp khóa API: Nội suy biến ${} và đường ống SecretRef

Cấu hình hỗ trợ viết `${VAR_NAME}` bên trong các trường chuỗi ký tự, hoặc sử dụng đối tượng `SecretRef`. Chúng tôi khuyến nghị lưu trữ toàn bộ khóa bí mật trong biến môi trường hoặc hệ thống quản lý khóa, tuyệt đối không để lộ văn bản thuần trong file cấu hình: Nhờ vậy tệp cấu hình có thể commit lên Git an toàn, dễ dàng kiểm toán, tái lập môi trường và tránh rò rỉ khóa bí mật xuống đĩa cứng.

**1. Dạng cơ bản: Nội suy biến môi trường `${}`**

Các provider tích hợp sẵn ưu tiên nạp qua biến môi trường, onboarding hoặc `openclaw models auth` để ghi vào auth profiles; dưới đây là hình thức dùng biến môi trường phổ biến nhất:

```bash
# Cách A: export trực tiếp
export OPENAI_API_KEY="..."

# Cách B: ghi vào ~/.openclaw/.env hoặc tệp .env tại thư mục dự án
OPENAI_API_KEY="..."
```

> [!NOTE]
> Khi khởi động, OpenClaw sẽ đọc biến môi trường theo thứ tự ưu tiên: `Biến môi trường tiến trình thực tế` > `Tệp .env thư mục hiện tại` > `~/.openclaw/.env`. **Lưu ý: Các biến định nghĩa trong tệp `.env` sẽ không thể ghi đè biến cùng tên đã tồn tại sẵn trong môi trường của tiến trình.**

**2. Dạng nâng cao: Sử dụng SecretRef kết nối đường ống quản lý khóa thống nhất**

Đối với các hệ thống triển khai cấp sản xuất, OpenClaw cung cấp một đường ống Secrets Pipeline thống nhất. Bạn không bị giới hạn ở biến môi trường mà có thể dùng định dạng đối tượng `SecretRef` để nạp an toàn, cho phép kết nối với nhiều nhà cung cấp bí mật khác nhau và kết hợp với hệ sinh thái lệnh `openclaw secrets` để kiểm toán phụ thuộc.

SecretRef chỉ áp dụng cho các trường thông tin tĩnh được schema hiện tại hỗ trợ rõ ràng; các tài liệu xác thực runtime như OAuth profile material sẽ không nhận SecretRef. Trước khi áp dụng nên dùng lệnh `openclaw config set --dry-run` hoặc `openclaw security audit` để xác minh. SecretRef hỗ trợ 3 loại nguồn `source`:

- `"env"`: Đọc từ biến môi trường (Phổ biến nhất)
- `"file"`: Đọc nội dung từ đường dẫn tệp tin
- `"exec"`: Thực thi lệnh và lấy kết quả từ luồng xuất chuẩn (stdout)

```javascript
{
  secrets: {
    providers: {
      default: { source: "env" },
    },
  },
  models: {
    providers: {
      "custom-proxy": {
        baseUrl: "https://my-proxy.internal/v1",
        api: "openai-completions",
        // Cách 1: Đọc an toàn từ biến môi trường qua SecretRef
        apiKey: { source: "env", provider: "default", id: "CUSTOM_PROXY_API_KEY" },
        models: [
          {
            id: "team-fast",
            name: "Team Fast Model",
            input: ["text"],
            contextWindow: 128000,
            contextTokens: 96000,
            maxTokens: 32000,
          },
        ],
      },
    },
  },
}
```

> [!WARNING]
> **Rủi ro rò rỉ khóa khi hệ thống tự động ghi đè cấu hình**: Nếu hệ thống cho phép tác nhân bên ngoài (như AI) sửa tệp cấu hình hoặc thực hiện đồng bộ hóa không đúng cách, các biến nội suy dạng `${VAR_NAME}` có xác suất nhỏ bị giải mã thành giá trị thực tế và ghi đè ngược thành văn bản thuần xuống đĩa. Việc sử dụng ngữ nghĩa đối tượng `SecretRef` sẽ giúp cô lập chặt chẽ luồng dữ liệu, ngăn ngừa hữu hiệu rủi ro này.

Lưu ý:
- Nhật ký log có cấu trúc và đầu ra chẩn đoán tuyệt đối không in khóa bí mật ở dạng văn bản thuần.
- Khi nghiệm thu, vui lòng dùng `openclaw security audit`, `models status` và khi cần thiết thì dùng `models status --probe`.

### 4.2.5 Đa khóa API & Hồ sơ xác thực (Auth Profiles): Cấu trúc dự phòng cho việc xoay tua và phát hành từng phần

Hiện tại OpenClaw không sử dụng các cấu trúc như `models.providers.*.keys` / `keyId` làm giao diện đa khóa tại runtime. Việc quản lý nhiều thông tin xác thực cho cùng một provider phải được thể hiện qua Auth profiles, `auth.order`, hoặc danh sách key hỗ trợ trong biến môi trường. Chúng tôi khuyến nghị tách thao tác "Bổ sung khóa mới" và "Chuyển đổi thứ tự mặc định" thành hai bước riêng biệt: Trước tiên thêm khóa mới và thử nghiệm lưu lượng nhỏ, sau đó điều chỉnh `auth.order` hoặc thứ tự biến môi trường, cuối cùng mới thu hồi khóa cũ.

Ví dụ cấu hình thứ tự hồ sơ xác thực (chỉ lưu metadata định tuyến, khóa thực tế vẫn nằm trong `auth-profiles.json` hoặc SecretRef):

```javascript
{
  auth: {
    profiles: {
      "openai:primary": {
        provider: "openai",
        mode: "api_key",
      },
      "openai:secondary": {
        provider: "openai",
        mode: "api_key",
      },
    },
    order: {
      openai: ["openai:primary", "openai:secondary"],
    },
  },
}
```

Đừng nhầm lẫn các tên biến như `<PROVIDER>_API_KEYS`, `<PROVIDER>_API_KEY_1` hay `OPENCLAW_LIVE_<PROVIDER>_KEY` là giao diện bể khóa chung được mọi provider hỗ trợ. Lộ trình xoay tua an toàn trong sản xuất là: Tạo thêm auth profile mới, điều chỉnh `auth.order`, và nạp khóa tĩnh qua SecretRef hoặc biến môi trường được tài liệu provider hỗ trợ rõ ràng. Lời khuyên xoay tua: Đừng thay đổi trực tiếp giá trị của cùng một biến môi trường ngay trong khung giờ phát sinh sự cố, vì điều đó sẽ làm mất dấu vết bằng chứng chẩn đoán; cách làm vững chắc là thêm một thông tin xác thực mới, đổi thứ tự profile, duy trì khóa cũ trong một khoảng thời gian quan sát rồi mới thu hồi.

### 4.2.6 Nghiệm thu kết nối: Dùng models status để kiểm chứng quan sát

Sau khi hoàn tất cấu hình, hãy dùng một bộ lệnh tối thiểu để nghiệm thu (đánh giá bằng kết quả thực tế, không dựa vào cảm tính):

```bash
openclaw doctor
openclaw models status
openclaw models status --probe
openclaw status --deep
```

- `doctor` thất bại: Sửa ngay lỗi đọc file cấu hình và các phụ thuộc runtime, không vội sửa prompt hay workflow.
- `models status` báo bất thường: Ưu tiên kiểm tra xem auth profile có bị thiếu không, OAuth có hết hạn không, biến môi trường có tồn tại không, tên biến trong chuỗi `${}` có viết đúng chính tả không.
- `models status --probe` thất bại: Kiểm tra lại tính hợp lệ của live auth phía provider, kết nối mạng đến máy chủ upstream, và tên mô hình có còn khả dụng hay không.
- `status --deep` không nhìn thấy provider/model mong muốn: Kiểm tra lại phân tầng cấu hình (xem `models.providers` và `agents.defaults.model` có bị đặt sai vị trí hay không).

### 4.2.7 Quản trị giới hạn tần suất (Rate Limit) & Hạn mức sử dụng

Các nhà cung cấp mô hình thường áp dụng chính sách giới hạn tần suất (Rate limit) đối với các lệnh gọi API. OpenClaw được thiết kế để xử lý linh hoạt các giới hạn này, tránh làm gián đoạn dịch vụ.

**Xử lý phản hồi HTTP 429 từ nhà cung cấp**

Khi nhận phản hồi HTTP 429 (Too Many Requests), đường luồng chính hiện tại của OpenClaw không phải là đứng yên chờ đợi theo cấp số nhân 1s/2s/4s trên cùng một key, mà là đánh dấu auth profile tương ứng vào trạng thái làm nguội (Cooldown), sau đó thử profile tiếp theo của cùng provider đó theo ngân sách; khi ngân sách cạn kiệt hoặc loại lỗi phù hợp để chuyển đổi, hệ thống sẽ kích hoạt chuỗi fallback mô hình (Xem chi tiết tại Mục 4.4).

Thang thời gian cooldown mặc định thường là 30 giây, 60 giây, sau đó tối đa lên tới 5 phút; cửa sổ thời gian cụ thể là chiến lược nội bộ của hệ thống, được quyết định kết hợp giữa phân loại lỗi và trạng thái profile. Nhật ký log có cấu trúc sẽ ghi lại các quyết định cooldown, xoay tua profile và fallback để phục vụ phân tích sự cố và thiết lập cảnh báo.

**Chiến lược cấu hình giới hạn tần suất**

Hiện tại giao diện cấu hình công khai không cung cấp các trường giới hạn chủ động cục bộ như `models.providers.*.rateLimit`. Việc quản trị giới hạn tần suất mô hình được chia thành 3 tầng:

1. **Bên trong OpenClaw**: Dựa vào cơ chế cooldown của auth profile, xoay tua profile trong cùng provider, chiến lược luân chuyển profile khi chạm rate limit và cơ chế fallback sang mô hình khác.
2. **Phía nhà cung cấp**: Thiết lập hạn mức chi tiêu (Billing limits), hạn mức dự án (Project quotas), rate limit cấp tổ chức hoặc phân quyền theo API key.
3. **Phía cổng vào (Ingress)**: Thực hiện định hình lưu lượng (Traffic shaping), xếp hàng và ngắt mạch (Circuit breaking) tại Reverse Proxy, hàng đợi tin nhắn, plugin hoặc Gateway nghiệp vụ.

**Sử dụng Fallback đa nhà cung cấp để loại bỏ điểm nghẽn đơn lẻ**

Cách làm vững chắc nhất cho các dịch vụ trọng yếu là cấu hình nhiều nhà cung cấp mô hình, để khi một nhà cung cấp liên tục bị chạm rate limit, hệ thống sẽ tự động chuyển sang nhà cung cấp dự phòng:

```javascript
{
  agents: {
    defaults: {
      model: {
        primary: "openai/gpt-5.5",
        fallbacks: [
          "anthropic/claude-sonnet-4-6",
        ],
      },
    },
  },
}
```

Nếu bạn sử dụng thuê bao ChatGPT/Codex OAuth, cấu hình hiện tại vẫn nên dùng định danh `openai/*`, trong đó thông tin thuê bao được thể hiện qua Codex/OpenAI auth profile và runtime; các định danh lịch sử như `openai-codex/*` nên được chuyển đổi bằng lệnh `openclaw doctor --fix`. Điểm mấu chốt là **phải giữ tính nhất quán giữa danh mục mô hình hiện tại, auth profile và lựa chọn runtime**. Nhờ vậy, ngay cả khi luồng chính tạm thời không khả dụng do chạm rate limit, yêu cầu vẫn tự động hạ cấp xuống mô hình thứ cấp hoặc nhà cung cấp dự phòng, bảo đảm tính liên tục của dịch vụ.

> **Bài học thực tế: Biến môi trường "rõ ràng đã đặt nhưng chương trình không đọc được"**
>
> Một cái bẫy triển khai rất phổ biến: Khai báo `export ANTHROPIC_API_KEY="..."` trong tệp `~/.bashrc`, nhưng khi OpenClaw khởi động dưới dạng dịch vụ systemd thì không tài nào đọc được biến này. Nguyên nhân là systemd không tự động nạp shell profile của người dùng. Giải pháp: Khai báo rõ ràng dòng `EnvironmentFile=/etc/openclaw/env` trong file unit của systemd, hoặc dùng lệnh `openclaw secrets configure` để đưa khóa bí mật vào hệ thống SecretRef.
