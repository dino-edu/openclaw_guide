## 12.2 Tự tạo Tool tùy biến: Cô lập tác dụng phụ trong ranh giới kiểm soát

Điểm khó của việc viết công cụ tùy biến (Custom Tools) không nằm ở việc "viết một hàm thực thi", mà nằm ở chỗ "làm thế nào để biến tác dụng phụ thành một năng lực kỹ thuật có thể kiểm soát, kiểm toán và hoàn tác được". Trong OpenClaw, Plugin chịu trách nhiệm đưa vào năng lực công cụ, Chính sách công cụ chịu trách nhiệm thu hẹp ranh giới có thể thực thi, còn cơ chế đa Agent và Sandbox chịu trách nhiệm cô lập các hành động rủi ro cao trong môi trường an toàn. Mục này tập trung vào phương pháp hiện thực hóa công cụ mở rộng, nhấn mạnh các ràng buộc xác định ở tầng cấu hình và lộ trình nghiệm thu có thể kiểm chứng.

### 12.2.1 Nguyên tắc tối thiểu của Custom Tool: Đầu vào kiểm chứng được, Đầu ra phát lại được

Trước khi đưa một công cụ vào hệ thống, bạn bắt buộc phải xác lập 3 bản giao ước kỹ thuật:

1. **Ràng buộc đầu vào**: Tham số bắt buộc phải kiểm chứng được định dạng và kiểu dữ liệu, tránh đưa "văn bản tự do" trực tiếp vào các công cụ có độ rủi ro cao.
2. **Ràng buộc đầu ra**: Kết quả trả về bắt buộc phải có cấu trúc, tránh việc bơm cả khối dữ liệu thô khổng lồ làm ngập lụt ngữ cảnh đối thoại.
3. **Ranh giới tác dụng phụ**: Thao tác ghi bắt buộc phải hỗ trợ khóa bất biến (Idempotency Key) hoặc có lộ trình hoàn tác đối soát, khi thất bại phải đưa ra các bước hướng dẫn con người kiểm tra thủ công.

Đây là những lằn ranh đỏ xác định không phụ thuộc vào độ thông minh của mô hình AI.

#### Ba phản mẫu thiết kế (Anti-patterns) điển hình

Ba phản mẫu dưới đây minh họa lý do vì sao 3 ràng buộc trên là không thể thiếu:

**Phản mẫu 1: Đưa văn bản tự do trực tiếp vào tham số lệnh Shell**

Một công cụ trích xuất dữ liệu nhận tên bảng do người dùng nhập vào làm tham số, không kiểm tra mà nhúng thẳng vào chuỗi truy vấn SQL. Kẻ tấn công có thể chèn chuỗi `; DROP TABLE users; --` dẫn đến mất sạch dữ liệu. Ràng buộc "Đầu vào kiểm chứng được" đòi hỏi tham số bắt buộc phải qua whitelist hoặc regex pattern, tuyệt đối không cho phép văn bản tự do tham gia vào các thao tác rủi ro cao.

**Phản mẫu 2: Đầu ra không có cấu trúc làm bùng nổ ngữ cảnh**

Một công cụ truy vấn log trả về nguyên trạng cả một tệp log khổng lồ, mô hình không thể phân tích nổi và buộc phải gọi nhiều lượt hỏi đáp lặp lại để hiểu nội dung. Hậu quả là cửa sổ ngữ cảnh bị tràn ngập bởi các dòng log rác, khiến việc suy luận về sau chậm chạp và dễ sinh ảo giác. Ràng buộc "Đầu ra có cấu trúc" yêu cầu công cụ phải tự lọc và tổng hợp trước, chỉ trả về các trường then chốt: `{ "error_count": 5, "latest_error": "...", "affected_services": [...] }`.

**Phản mẫu 3: Thao tác ghi thiếu khóa bất biến khiến việc thử lại tạo đơn trùng**

Một công cụ tạo ticket hỗ trợ không có logic khử trùng lặp; khi mạng bị timeout kích hoạt thử lại, hệ thống sẽ tạo ra nhiều ticket trùng nhau. Dù mô hình sau đó có phát hiện ra trùng lặp thì cũng không thể tự hoàn tác, buộc con người phải vào dọn dẹp thủ công. Ràng buộc "Tác dụng phụ có thể hoàn tác" đòi hỏi thao tác ghi bắt buộc phải hỗ trợ khóa bất biến (như ID yêu cầu) hoặc cung cấp bước rollback tường minh.

### 12.2.2 Đưa công cụ vào Chính sách: Quy tắc phân tầng & Từ chối ưu tiên

Quản trị công cụ phải được thiết lập tại tầng Chính sách công cụ. Quy tắc từ chối (`deny`) luôn ưu tiên hơn quy tắc cho phép (`allow`):

```javascript
{
  tools: {
    profile: 'coding',
    deny: ['group:runtime'],
  },
  channels: {
    telegram: {
      groups: {
        '*': {
          tools: { deny: ['write', 'edit', 'apply_patch'] },
        },
      },
    },
    discord: {
      groups: {
        ops: {
          tools: { deny: ['group:runtime'] },
        },
      },
    },
  },
}
```

Bằng cách này, nhóm Telegram chỉ có quyền đọc và tìm kiếm; nhóm `ops` trên Discord được dùng các công cụ ghi file nhưng vẫn bị cấm gọi các công cụ thực thi runtime trên máy chủ host.

#### Cú pháp TypeScript khi đăng ký Công cụ

Plugin OpenClaw dùng TypeScript để đăng ký công cụ. Schema tham số thường dùng `Type.Object()` từ thư viện TypeBox (sinh JSON Schema), logic thực thi nằm trong hàm `execute(id, params)`. Dưới đây là quy trình đăng ký chuẩn mực:

```typescript
import { Type } from "@sinclair/typebox";

api.registerTool({
  name: "create_ticket",
  description: "Create a support ticket with validation",
  parameters: Type.Object({
    title: Type.String({ minLength: 5, maxLength: 200 }),
    category: Type.Union([
      Type.Literal("bug"),
      Type.Literal("feature"),
      Type.Literal("ops"),
    ]),
    priority: Type.Number({ minimum: 1, maximum: 5 }),
    assignee_id: Type.String({ pattern: "^[0-9a-f]+$" }),
  }),
  async execute(id, params) {
    // Tầng thực thi (Kèm xử lý lỗi)
    try {
      const ticket = await ticketService.create({
        title: params.title,
        category: params.category,
        priority: params.priority,
        assignee_id: params.assignee_id,
        idempotency_key: id, // Dùng chính ID lượt gọi công cụ làm khóa bất biến
      });

      // Kết quả trả về có cấu trúc
      return {
        content: [{ type: "text", text: `Ticket ${ticket.id} created` }],
        details: {
          ticketId: ticket.id,
          status: ticket.status,
          createdAt: ticket.createdAt,
        },
      };
    } catch (err) {
      return { content: [{ type: "text", text: "internal error" }] };
    }
  },
});
```

Điểm then chốt:
1. Schema tham số dùng `Type.Object()` của TypeBox, được framework tự động xác thực trước khi gọi, không cần viết lại validation trong hàm execute.
2. Tham số `id` trong `execute(id, params)` là định danh lượt gọi do framework cấp phát, có thể dùng trực tiếp làm khóa bất biến (Idempotency Key).
3. Kết quả trả về tuân thủ `AgentToolResult`: Nội dung hiển thị cho mô hình nằm trong `content`, các trường dữ liệu có cấu trúc phục vụ theo vết nằm trong `details`.
4. Mỗi công cụ đăng ký qua `api.registerTool(...)` bắt buộc phải được khai báo trong `contracts.tools` của tệp `openclaw.plugin.json`.

### 12.2.3 Quản lý phiên bản công cụ & Vòng đời

Các công cụ trong môi trường sản xuất không thể thay đổi tùy tiện. Cần thiết lập chiến lược phiên bản rõ ràng để tránh làm gãy các Agent đang vận hành:

1. Khai báo tính tương thích ngược trong định nghĩa công cụ. Khi tham số hoặc hành vi thay đổi, phải đánh dấu rõ tính tương thích.
2. Thiết lập thời gian chờ loại bỏ (Deprecation period) từ 180 ngày trở lên.
3. Ghi nhận số hiệu phiên bản trên chuỗi gọi công cụ để tiện truy vết sai lệch hành vi.

Mẫu tệp theo dõi phiên bản nội bộ (`tool-versions.json`):

```javascript
{
  tools: [
    {
      id: 'query_database',
      versions: {
        '1.0': {
          status: 'deprecated',
          params: ['query', 'timeout'],
          deprecatedAt: '2026-01-15',
          sunsetsAt: '2026-07-15',
          migrateToVersion: '1.1',
        },
        '1.1': {
          status: 'active',
          params: ['query', 'timeout', 'schema'],
        },
      },
    },
  ],
}
```

Theo dõi phiên bản qua log:

```bash
openclaw logs --follow --json | jq -c 'select(.type=="log") | (.raw | fromjson? // {}) as $raw | select(($raw|tostring)|contains("query_database")) | {time, level, subsystem, raw:$raw}'
```

### 12.2.4 Phối hợp & Điều phối chuỗi công cụ (Orchestration)

Tính bất biến của một công cụ đơn lẻ là chưa đủ đối với các tác vụ phức tạp. Khi nhiều công cụ cần hiệp đồng tác chiến, mối quan hệ phụ thuộc, thứ tự thực thi và luồng dữ liệu bắt buộc phải được khai báo tường minh bằng đồ thị phụ thuộc (Dependency Graph), thay vì phó mặc cho sự "suy luận tự do" của mô hình:

```javascript
{
  tools: {
    orchestration: {
      workflows: [
        {
          id: 'deploy_service',
          steps: [
            {
              tool: 'validate_config',
              params: { config_path: '/config.yaml' },
              required: true,
              onFailure: 'abort',
            },
            {
              tool: 'build_image',
              params: { source: '/src', tag: 'service:latest' },
              requires: ['validate_config'],
              requiredOutputSchema: { passed: 'boolean' },
            },
            {
              tool: 'push_registry',
              params: { image: 'service:latest', registry: 'internal' },
              requires: ['build_image'],
              requiredOutputSchema: { imageId: 'string' },
            },
            {
              tool: 'deploy_canary',
              params: { image: 'service:latest', replicas: 1 },
              requires: ['push_registry'],
              onFailure: 'rollback_to:previous_image',
            },
          ],
        },
      ],
    },
  },
}
```

### 12.2.5 Cách ly thực thi cho các công cụ có độ rủi ro cao

Đối với các công cụ can thiệp sâu vào hệ thống (chạy code, sửa file OS), khuyến nghị áp dụng mô hình "Chỉ một số ít Agent nắm quyền ghi":

1. Đại đa số Agent cổng vào chỉ được phép dùng công cụ đọc và chẩn đoán.
2. Một số ít Agent vận hành chuyên trách được phép dùng công cụ ghi trong môi trường Sandbox và chịu sự kiểm toán nghiêm ngặt.
3. Tệp cấu hình chứng thư `~/.openclaw/agents/<agentId>/agent/auth-profiles.json` định nghĩa các quyền hạn khả dụng trong môi trường sandbox, bảo đảm công cụ ghi chỉ hoạt động trong phạm vi được cấp phép.

### 12.2.6 Nghiệm thu & Chẩn đoán sự cố

Quy trình nghiệm thu 2 bước sau khi triển khai công cụ mới:

1. **Nghiệm thu cấu hình**: Dùng `openclaw config get tools --json` để xác nhận chính sách khai báo đã nạp, dùng `openclaw sandbox explain --agent <id> --json` để xem chính sách sandbox thực tế.
2. **Nghiệm thu hành vi**: Dùng nhật ký log có cấu trúc để quan sát sự kiện gọi và từ chối công cụ, bảo đảm quy tắc deny thực sự phát huy tác dụng.

```bash
openclaw config get tools --json
openclaw sandbox explain --agent <id> --json
openclaw logs --follow --json
```
