## 13.1 Tình huống thực tế: Trợ lý công việc nhóm Lark/Slack cho doanh nghiệp

### 13.1.1 Định nghĩa bài toán & Ràng buộc kịch bản

Một đội ngũ kỹ thuật phần mềm quy mô 30 người hàng ngày cộng tác qua Lark/Feishu, mong muốn xây dựng một trợ lý thông minh ngay trong nhóm chat với các năng lực:

- Giải đáp các thắc mắc về tài liệu kỹ thuật nội bộ và kho mã nguồn.
- Tự động tổng hợp hoạt động Pull Request (PR) hàng ngày trên GitHub.
- Tra cứu và tạo mới ticket trên Jira bằng ngôn ngữ tự nhiên.
- Kiểm soát phân quyền dựa trên vai trò của người gửi (Kỹ sư vs Khách vãng lai).

Điều kiện ràng buộc: Phải hoạt động trực tiếp bên trong nhóm chat Lark hiện có, không bổ sung hạ tầng phức tạp ngoài OpenClaw Gateway.

### 13.1.2 Vòng lặp tối thiểu: Chạy thông luồng đơn công cụ trên một kênh duy nhất

Bắt đầu từ cấu hình đơn giản nhất để kiểm chứng quy trình cơ bản của bot trong nhóm chat. Chúng tôi sử dụng một công cụ tìm kiếm cơ sở tri thức kết hợp kênh Feishu/Lark để vẽ nên một bộ khung thiết kế mẫu:

> [!WARNING]
> Cấu hình dưới đây **không phải là tệp mẫu hoàn chỉnh có thể dán vào chạy ngay**. Các kịch bản về Lark/Slack có sự tiến hóa rất nhanh giữa các phiên bản. Trước khi thao tác, hãy đối soát với `openclaw config schema` hoặc trang Config trên Dashboard để ánh xạ ý đồ thiết kế vào các trường dữ liệu thực tế trên máy bạn.

Dưới đây là bộ khung cấu hình tối thiểu:

```jsonc
{
  "profile": "default",
  "version": "1.0.0",
  "agents": {
    "entries": {
      "group_assistant": {
        "name": "Trợ lý nhóm công việc",
        "instructions": "Bạn là trợ lý thông minh của đội ngũ kỹ sư doanh nghiệp.\nNgười dùng sẽ đặt câu hỏi trong nhóm Lark, nhiệm vụ của bạn là:\n1. Tìm kiếm trong cơ sở tri thức nội bộ để trả lời các câu hỏi thường gặp\n2. Giữ câu trả lời súc tích, chuyên nghiệp\n3. Nếu trong tri thức không có câu trả lời, hãy thành thật trả lời \"Tôi không tìm thấy tài liệu liên quan\"",
        "model": "<provider/low-latency-model>",
        "tools": {
          "allow": ["knowledge_base_search"]
        }
      }
    }
  },
  "tools": {
    "knowledge_base_search": {
      "description": "Tìm kiếm tài liệu và chú thích code trong cơ sở tri thức nội bộ",
      "// implementation": "Hiện thực hóa qua plugin tùy biến hoặc bọc lại memory_search; ở đây chỉ thể hiện hợp đồng công cụ"
    }
  },
  "channels": {
    "feishu": {
      "enabled": true,
      "domain": "feishu",
      "accounts": {
        "main": {
          "appId": "${LARK_APP_ID}",
          "appSecret": "${LARK_APP_SECRET}",
          "groupPolicy": "allowlist",
          "groupAllowFrom": ["<feishu-chat-id>"],
          "requireMention": true
        }
      },
      "dmPolicy": "pairing"
    }
  }
}
```

Làm theo các bước tại [Chương 7: Mục 7.2 Hướng dẫn kết nối Lark/Feishu](../07_multi_agent/7.2_lark_integration.md) để hoàn tất cấu hình ứng dụng và gắn kết kênh, sau đó khởi động Gateway:

```bash
openclaw gateway start
```

Vào nhóm chat Lark tag (@) tên bot để đặt câu hỏi. Lưu ý: Mặc định phản hồi cuối cùng của bot trong nhóm chat thường là phản hồi nội bộ/riêng tư; nếu muốn bot xuất câu trả lời công khai hiển thị cho cả nhóm nhìn thấy, Agent cần gọi công cụ `message(action=send)` tường minh hoặc cấu hình `messages.groupChat.visibleReplies: "automatic"`.

### 13.1.3 Bóc tách cấu hình phân tầng

Từng bước bổ sung các tính năng nâng cao:

#### 1. Bổ sung công cụ: Phân tích GitHub PR & Quản lý Ticket Jira

Cập nhật danh sách `agents.entries.*.tools.allow` để thêm 2 công cụ mới:

```json
{
  "tools": {
    "allow": [
      "knowledge_base_search",
      "github_pr_analyzer",
      "jira_issue_manager"
    ]
  }
}
```

Khai báo hợp đồng công cụ ở tầng plugin:

```jsonc
"tools": {
  "knowledge_base_search": {
    "// implementation": "Bọc memory_search hoặc plugin cơ sở tri thức tùy biến"
  },
  "github_pr_analyzer": {
    "description": "Phân tích hoạt động PR trong 24 giờ qua trên kho GitHub",
    "// implementation": "Custom plugin tool, token nạp qua SecretRef / biến môi trường"
  },
  "jira_issue_manager": {
    "description": "Tạo mới và tra cứu ticket trên Jira",
    "// implementation": "Custom plugin tool, ánh xạ trường dữ liệu quản lý nội bộ trong plugin"
  }
}
```

#### 2. Kiểm soát phân quyền: Chính sách truy cập dựa trên vai trò (RBAC)

Ma trận phân quyền logic giữa kỹ sư và khách vãng lai:

```text
engineer: knowledge_base_search, github_pr_analyzer, jira_issue_manager
guest:    knowledge_base_search
```

Cách triển khai thực tế tùy thuộc vào từng kênh: Trên Slack có thể dùng `toolsBySender` ở cấp channel/group để cấp thêm (`alsoAllow`) công cụ đặc quyền cho tài khoản kỹ sư; trên Feishu/Lark trước tiên dùng `allowFrom` để kiểm soát ai được kích hoạt bot trong nhóm, sau đó phân quyền công cụ chi tiết thông qua Hook `before_tool_call` để từ chối động dựa trên danh tính người gửi tra cứu từ danh bạ doanh nghiệp. Xem chi tiết tại [Mục 5.2 Chính sách Tool](../05_tools_skills/5.2_tool_policy.md) và [Mục 11.4 Hàng rào bảo vệ](../11_reliability_security/11.4_guardrails.md).

#### 3. Bổ sung tác vụ định kỳ: Bản tóm tắt PR hàng ngày

Định nghĩa tác vụ định kỳ Cron trên Gateway:

```json
{
  "job_spec_example": {
    "daily_pr_summary": {
      "schedule": "0 16 * * *",
      "agent": "group_assistant",
      "tool": "github_pr_analyzer",
      "channel": "feishu",
      "instruction": "Tạo bản tóm tắt hoạt động PR trong 24 giờ qua: 1) Số PR mở mới, 2) Số PR đã merge, 3) Danh sách PR đang chờ review. Trình bày định dạng Markdown súc tích.",
      "timezone": "Asia/Ho_Chi_Minh"
    }
  }
}
```

Tác vụ sẽ kích hoạt vào đúng 16:00 hàng ngày theo giờ địa phương (`timezone: "Asia/Ho_Chi_Minh"`), tự động gửi bản tóm tắt vào nhóm chat đích qua `to: "<feishu-chat-id>"`. Chi tiết xem tại [Chương 8: Tự động hóa và tác vụ định kỳ](../08_automation_ops/README.md).

### 13.1.4 Checklist nghiệm thu & Các điểm sự cố thường gặp

Quy trình nghiệm thu từng hạng mục:

1. **Bot xử lý tin nhắn nhóm**: Tag tên bot trong nhóm Lark, xác nhận trong log xuất hiện agent turn và tin nhắn phản hồi hiển thị trong nhóm.
2. **Tìm kiếm tri thức có kết quả**: Hỏi một câu hỏi có thật trong tài liệu (ví dụ: "Tài liệu API ở đâu"), xác nhận bot trả lời đúng nội dung.
3. **Phân quyền có hiệu lực**: Dùng tài khoản khách yêu cầu "Hãy phân tích các PR gần đây", xác nhận bot phản hồi từ chối: "Bạn không có quyền sử dụng tính năng này".
4. **Tác vụ định kỳ kích hoạt đúng giờ**: Kiểm tra log xác nhận tác vụ chạy đúng 16:00 chiều.

Bảng sự cố thường gặp và cách khắc phục:

| Vấn đề | Nguyên nhân khả dĩ | Các bước chẩn đoán |
|---|---|---|
| **Bot không trả lời** | Quyền ứng dụng Lark chưa duyệt, thứ tự đăng ký sự kiện sai, cấu hình kênh không khớp phiên bản | Xem lại cảnh báo tại [Mục 7.2](../07_multi_agent/7.2_lark_integration.md); đối chiếu cấu hình với `config.schema` trên Dashboard |
| **Không tìm thấy kết quả tri thức** | Chỉ mục bộ nhớ OpenClaw chưa ghi, hoặc cấu hình plugin tìm kiếm tùy biến bị lệch đường dẫn | Kiểm tra chỉ mục `memory_search` / memory-core; kiểm tra log plugin tùy biến |
| **Khách vẫn gọi được công cụ đặc quyền** | `toolsBySender`, chính sách công cụ hoặc hook tùy biến chưa khớp | Dùng `openclaw sandbox explain` kiểm tra chính sách có hiệu lực; đặt logic điều kiện trong `before_tool_call` hook |
| **Tác vụ định kỳ không chạy** | Cấu hình múi giờ sai hoặc cú pháp biểu thức cron không hợp lệ | Kiểm tra `timezone` có phải là tên múi giờ IANA hợp lệ không; kiểm tra cú pháp cron 5 trường |

### 13.1.5 Mở rộng lên môi trường sản xuất cần bổ sung những gì

Khi chuyển từ môi trường thử nghiệm lên môi trường sản xuất:

- **Triển khai trên Kubernetes**: Đóng gói thành container Pod có khả năng tự động co giãn và nhiều bản sao (Replicas). Xem chi tiết tại [Mục 12.4 Bản thiết kế sản xuất](../12_extension_engineering/12.4_production_blueprint.md).
- **Giám sát và Cảnh báo**: Kết nối Prometheus/DataDog để giám sát thời gian phản hồi, tỷ lệ lỗi, tần suất gọi công cụ.
- **Hỗ trợ đa kênh đồng thời**: Mở rộng kết nối song song Slack, Discord, Telegram, WhatsApp...
- **Nhật ký kiểm toán**: Lưu trữ độc lập toàn bộ các lượt gọi công cụ và kết quả kiểm tra quyền hạn phục vụ rà soát an ninh.
