## 14.2 Tối ưu hóa độ trễ (Latency) & Băng thông xử lý (Throughput)

Mục này xuất phát từ **Mô hình độ trễ hình thức** và **Mô hình chi phí cấu trúc** để giúp bạn nhận diện các điểm nghẽn hiệu năng và đòn bẩy tối ưu hóa của OpenClaw. Thay vì chỉnh sửa tham số theo cảm tính, việc xây dựng mô hình toán học rõ ràng sẽ giúp bạn tối ưu hóa trúng đích.

Trước tiên, tổng độ trễ xử lý của một yêu cầu Agent hoàn chỉnh (End-to-End) có thể phân rã thành 4 thành phần bất khả quy:

```text
Tổng độ trễ (E2E) = Độ trễ suy luận LLM + Độ trễ I/O công cụ + Độ trễ thực thi Sandbox + Chi phí điều phối
```

### 14.2.1 Mô hình hóa phân rã độ trễ

Dưới đây là phân tích chi tiết từng thành phần độ trễ:

#### 1. Độ trễ suy luận LLM ($T_{llm}$)

$$T_{llm} = T_{ttft} + T_{tokens} \times k$$

Trong đó:
- $T_{ttft}$: Thời gian sinh Token đầu tiên (Time To First Token). Thông thường từ 30–150ms, tùy thuộc vào mô hình và nhà cung cấp.
- $T_{tokens}$: Thời gian trung bình để sinh mỗi Token tiếp theo. Thông thường từ 20–50ms.
- $k$: Số lượng Token xuất ra (Output Tokens).

**Đòn bẩy tối ưu**:
- Lựa chọn mô hình có độ trễ thấp (ví dụ $T_{ttft}$ của Claude Haiku 4.5 thấp hơn rõ rệt so với Claude Opus).
- Giảm số lượng Token đầu ra (thông qua prompt tinh gọn, yêu cầu định dạng JSON ngắn gọn).
- Bật cơ chế xuất dạng luồng (Streaming), giúp người dùng nhìn thấy phản hồi chữ chạy ngay lập tức thay vì ngồi đợi trong im lặng.

#### 2. Độ trễ I/O của công cụ ($T_{tool}$)

Thời gian gọi công cụ tuần tự xấp xỉ bằng:

$$T_{tool,serial} = \sum_{i=1}^{n} (T_{latency\_i} + T_{processing\_i})$$

Khi gọi công cụ song song, thời gian sẽ tiệm cận với công cụ chậm nhất trên đường găng (Critical path) cộng với chi phí điều phối:

$$T_{tool,parallel} = \max_i(T_{latency\_i} + T_{processing\_i}) + T_{coordination}$$

Trong đó:
- $T_{latency\_i}$: Độ trễ khứ hồi mạng của công cụ thứ $i$ (thường từ 10–500ms).
- $T_{processing\_i}$: Thời gian xử lý nội bộ của công cụ đó.
- $n$: Số lượng công cụ được gọi.

**Đòn bẩy tối ưu**:
- **Song song hóa**: Nếu các tác vụ không phụ thuộc dữ liệu lẫn nhau, hãy ưu tiên dùng `sessions_spawn` / tác vụ ngầm hoặc cấu hình concurrency của hàng đợi Gateway để chạy song song.
- **Bộ nhớ đệm (Caching)**: Lưu cache kết quả của các lượt gọi công cụ trùng lặp để triệt tiêu độ trễ mạng.
- **Timeout & Hạ cấp**: Thiết lập timeout ở từng cấp (agent timeout, cron timeout, tool timeout); khi hết giờ thì trả về câu trả lời mặc định thay vì treo vô hạn.

Việc chuyển đổi từ gọi tuần tự sang gọi song song có thể giúp giảm độ trễ từ 800ms xuống còn 500ms (cải thiện 37.5%).

#### 3. Độ trễ thực thi trong Sandbox ($T_{sandbox}$)

$$T_{sandbox} = T_{startup} + T_{execution} + T_{teardown}$$

Trong đó:
- $T_{startup}$: Thời gian khởi động container sandbox (thường từ 100–500ms).
- $T_{execution}$: Thời gian thực thi mã lệnh thực tế của người dùng.
- $T_{teardown}$: Thời gian dọn dẹp và hủy container.

**Chiến lược tối ưu**:
- **Tái sử dụng Sandbox**: Đối với các lượt chạy liên tiếp của cùng một Agent, tái sử dụng thực thể sandbox thay vì mỗi lần đều tạo mới (tiết kiệm 200–300ms).
- **Làm ấm trước (Pre-warming)**: Khởi động sẵn các container trong lúc nhàn rỗi để giảm $T_{startup}$.
- **Tối ưu hóa Docker Image**: Dùng các base image siêu nhẹ (Alpine/Distroless) để giảm thời gian nạp.

#### 4. Chi phí điều phối của hệ thống ($T_{orchestrator}$)

$$T_{orchestrator} = T_{queue} + T_{dispatch} + T_{serialization} + T_{context\_loading}$$

Trong đó:
- $T_{queue}$: Thời gian chờ đợi trong hàng đợi Command Queue.
- $T_{dispatch}$: Thời gian định tuyến tin nhắn tới Agent mục tiêu (thường 1–5ms).
- $T_{serialization}$: Thời gian tuần tự hóa ngữ cảnh và prompt.
- $T_{context\_loading}$: Thời gian đọc ngữ cảnh phiên từ ổ đĩa/bộ nhớ.

**Đòn bẩy tối ưu**:
- **Giảm khối lượng nạp ngữ cảnh**: Dùng `contextPruning` và `compaction` để giảm dung lượng dữ liệu cần đọc.
- **Điều phối bất đồng bộ**: Dùng async cho các nhánh không nằm trên đường găng.
- **Bộ nhớ đệm trước**: Giữ ngữ cảnh của các phiên thường xuyên hoạt động trong RAM.

### 14.2.2 Sự tích lũy độ trễ trong hệ thống đa Agent

$$T_{total} = \sum_{i=1}^{N} T_{base\_i} + T_{routing} + T_{context\_transfer}$$

**Quan sát mấu chốt**:
- Cứ mỗi một bước nhảy qua Agent mới (Hop), hệ thống sẽ gánh thêm từ 10–50ms chi phí chuyển giao ngữ cảnh và định tuyến.
- Chuỗi điều phối quá sâu (ví dụ: Agent A → Agent B → Agent C → Agent D) có thể chậm hơn từ 50–200ms so với mô hình đơn Agent.
- **Lời khuyên kiến trúc**: Ưu tiên mô hình điều phối "rộng và nông" (các Agent chạy song song) thay vì mô hình "hẹp và sâu" (nhiều Agent nối đuôi nhau).

### 14.2.3 Mô hình chi phí có cấu trúc

```text
Tổng chi phí một yêu cầu = Chi phí LLM + Chi phí Công cụ + Chi phí Lưu trữ + Chi phí Hạ tầng
```

#### 1. Chi phí LLM ($C_{llm}$)

$$C_{llm} = n_{input} \times P_{input} + n_{output} \times P_{output}$$

**Ví dụ thực tế** (Đơn giá tham khảo Claude Sonnet 4.6: $3/1M input, $15/1M output):
- Trung bình mỗi yêu cầu tốn 2000 Token đầu vào + 500 Token đầu ra.
- Chi phí LLM cho 1 request:
  $$C_{llm} = (2000 \times 0.000003 + 500 \times 0.000015) = 0.006 + 0.0075 = \$0.0135 \text{ / yêu cầu}$$

#### 2. Chi phí công cụ ($C_{tool}$)

$$C_{tool} = \sum_{i=1}^{n} (\text{Đơn giá API}_i \times \text{Số lượt gọi}_i + \text{Dung lượng dữ liệu}_i \times \text{Đơn giá}_i)$$

Ví dụ:
- Google Search API: $5 / 1000 lượt truy vấn
- Đọc PostgreSQL: $0.25 / 1 triệu lượt
- Đọc AWS S3: $0.0004 / 10.000 lượt

#### 3. Chi phí lưu trữ ($C_{storage}$)

$$C_{storage} = \text{Số phiên hoạt động} \times \text{Dung lượng trung bình} \times \text{Đơn giá đĩa} + \text{Dung lượng log kiểm toán} \times \text{Đơn giá}$$

#### 4. Chi phí hạ tầng ($C_{infra}$)

Chi phí máy chủ, Gateway và tài nguyên tính toán:

| Quy mô | Mô hình hạ tầng |
|---|---|
| Nhỏ (< 100 req/ngày) | Cloud SaaS, trả theo lượt gọi thực tế |
| Vừa (100 – 10.000 req/ngày) | Máy chủ tự lưu trữ (Self-hosted) + Instance đặt trước |
| Lớn (> 10.000 req/ngày) | Cụm hạ tầng chuyên dụng + Hợp đồng dung lượng cam kết |

### 14.2.4 Ví dụ phân tích chi phí thực chiến

Giả sử vận hành một Agent CSKH doanh nghiệp:
- 5.000 tin nhắn mỗi ngày (khoảng 150.000 tin nhắn/tháng)
- Trung bình mỗi tin nhắn: 2000 Token đầu vào + 500 Token đầu ra
- Trung bình 2 lượt gọi API công cụ mỗi tin nhắn
- Lưu trữ phiên trong 30 ngày
- Sử dụng Claude Sonnet 4.6

**Bảng phân rã chi phí hàng tháng (Trước khi tối ưu)**:

| Hạng mục | Đơn giá | Số lượng | Chi phí hàng tháng |
|---|---|---|---|
| LLM (Đầu vào) | $3 / 1M | 300M tokens | $900 |
| LLM (Đầu ra) | $15 / 1M | 75M tokens | $1125 |
| Lượt gọi API công cụ | $5 / 1000 | 300K calls | $1500 |
| Lưu trữ trạng thái | $0.023 / GB | 75 GB | $1.70 |
| Máy chủ tính toán (2 node t3.xlarge) | $0.1664 / giờ | 1460 giờ | $243 |
| **TỔNG CHI PHÍ** | | | **$3769.70** |

**Phương án tối ưu hóa**:
1. 80% câu hỏi đơn giản chuyển sang dùng Haiku → Tiết kiệm ~$1080
2. Kích hoạt `agents.defaults.compaction` nén ngữ cảnh → Tiết kiệm $120
3. Thiết lập bộ nhớ đệm Cache cho công cụ (giảm 40% lượt gọi API ngoài) → Tiết kiệm $600
4. Tối ưu cấu hình máy chủ (dùng 2 node t3.small thay thế) → Tiết kiệm ~$212.60

**Chi phí sau tối ưu**: **Khoảng $1757 / tháng** (Giảm tới **53%** chi phí vận hành).

### 14.2.5 Sự đánh đổi giữa Hiệu năng và Chi phí

| Hướng tối ưu | Tác động hiệu năng | Tác động chi phí | Kịch bản khuyến nghị |
|---|---|---|---|
| **Dùng model nhanh hơn** | ↑ Nhanh hơn | ↑ Đắt hơn | Nhạy cảm độ trễ (CSKH, Chat thời gian thực) |
| **Dùng model rẻ hơn** | ↓ Chậm hơn đôi chút | ↓ Rẻ hơn nhiều | Tác vụ không cần thời gian thực (Xử lý dữ liệu ngầm) |
| **Gọi công cụ song song** | ↑ Nhanh hơn rõ rệt | ↔ Không đổi | Luôn luôn khuyến nghị áp dụng |
| **Nén ngữ cảnh** | ↓ Chậm hơn xíu* | ↓ Rất rẻ | Các phiên đối thoại dài |
| **Bật bộ nhớ đệm Cache** | ↑ Nhanh hơn | ↓ Rẻ hơn | Lựa chọn đôi bên cùng có lợi (Win-win) |

*\* Lưu ý: Nén ngữ cảnh có thể khiến chất lượng câu trả lời suy giảm nhẹ 1–5%, cần làm kiểm thử A/B để kiểm chứng.*

### 14.2.6 Bộ công cụ chẩn đoán hiệu năng

Mở tính năng trace chẩn đoán:

```bash
/trace on
```

Theo dõi dòng sự kiện trong log để phân tích độ trễ:

```bash
openclaw logs --follow --json
```

Đoạn phân tích dòng thời gian mẫu:
